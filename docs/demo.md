# Linux Agent — Demonstration Script

This document is the run sheet for the final presentation. It has three paths:

- **A. Read-only real-host demo** — always safe, no root.
- **B. Real configuration change** — requires the one-time privileged install.
- **C. Isolated lab apply/rollback** — no root, reproducible, the recommended fallback.

Total time: 8–10 minutes. Keep a terminal at 120+ columns and a second terminal for
`journalctl`/backups if possible.

---

```bash
cd /home/lcsang/linux-agent

.venv/bin/python agent.py --list-tools | tail -5

# Read-only checks

.venv/bin/python - <<'PY'
import asyncio, os, sys
from linux_agent.agent.client import open_stdio_session
async def main():
    env = dict(os.environ)
    stack, s = await open_stdio_session(sys.executable, ["server.py"], cwd=".", env=env)
    async with stack:
        r = await s.call_tool("system_overview", {})
        print("\n".join(getattr(c, "text", "") for c in r.content))
asyncio.run(main())
PY
```

If `GROQ_API_KEY` is missing, set it in `.env` before the demo. If the network is down,
use the lab path with `--list-tools` plus the direct MCP calls; the tools still run.

Optional: start a second terminal that follows the audit log:

```bash
tail -f logs/audit.jsonl
```

## A. Read-only real-host demo (3 minutes)

### A1. Health summary

Prompt:

```text
Give me a short health summary of this machine: host, uptime, disk usage and whether
nginx is running. Use the tools.
```

What the audience should see:

1. The tool list is printed at startup.
2. The agent calls `system_overview`, `disk_usage` and `service_status`.
3. The final answer is a table with real values (hostname, uptime, `/` usage, nginx
   active).

Talking points:

- The model did not guess; it called typed tools.
- The tools are read-only and annotated with `readOnlyHint=true`.
- Every call is in `logs/audit.jsonl`.

### A2. Service triage

```text
Is nginx healthy? Show the last 10 journal lines and tell me if any systemd units failed.
```

Expected tool path: `service_status`, `service_logs`, `failed_units`.

### A3. Dry-run change

```text
Plan a safe change of nginx client_max_body_size to 20m. Inspect the current values,
then show the dry-run diff. Do not apply it.
```

Expected output includes a unified diff to
`/etc/nginx/conf.d/99-linux-agent.conf` and the line `DRY RUN`. Confirm:

```bash
ls -l /etc/nginx/conf.d/99-linux-agent.conf 2>&1 || echo "dry run: file absent, as expected"
```

Talking point: a dry run does not need approval because it cannot change the host.

## B. Real configuration change (3 minutes)

**Prerequisite:** the privileged helpers have been installed once:

```bash
sudo scripts/install_privileged.sh --user "$USER" --units "nginx"
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh list
```

If the install was already done, skip the commands and just show the rule:

```bash
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh list
```

Start writes for this session:

```bash
LINUX_AGENT_ALLOW_WRITE=1 .venv/bin/python agent.py
```

Prompt:

```text
Inspect nginx, then change client_max_body_size to 20m. Show the diff first, ask me
before applying, then apply and reload. Verify the value afterwards.
```

Expected flow:

1. `nginx_list_parameters` / `nginx_get_parameter` — inspect.
2. `nginx_set_parameter(dry_run=true)` — diff.
3. Agent prints an approval prompt with the tool name and arguments.
4. Type `y`.
5. The helper runs through sudo, backs up, writes, runs `nginx -t`, reloads.
6. Agent verifies with `nginx_get_parameter`.
7. Show the backup:

```bash
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh list-backups
```

8. Roll back:

```text
List the nginx backups and roll back the most recent one. Ask me before applying.
```

Type `y`. The helper creates a safety backup, restores, tests and reloads.

Talking points:

- The approval prompt is generated by the agent, not by the model.
- The helper validates again; the model cannot bypass it.
- The backup is timestamped and contains an `absent.map` if the file did not exist.
- The audit log records both the dry run and the apply.

**If something goes wrong:** do not improvise on `/etc/nginx`. Run:

```bash
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh list-backups
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh status
```

The helper refuses to apply a value that fails `nginx -t`; a failed test restores the
backup automatically.

## C. Isolated lab demo — fallback (2 minutes)

Use this if sudo is unavailable, the network is unreliable, or the host is shared.

```bash
bash scripts/lab_demo.sh
```

The script prints:

1. Initial lab `nginx.conf`.
2. `nginx_list_parameters`.
3. Dry-run diff, no write.
4. Apply `20m`, `nginx -t` passed, backup id.
5. Verify `20m`.
6. List backups.
7. Rollback with a safety backup.
8. Verify `unset`.
9. Server audit tail.

It uses the **real** `server.py` and the **real** `scripts/nginx_param.sh`, but a temporary
config tree and fake `nginx`/`systemctl`. No root and no `/etc/nginx` changes.

Optional natural-language turn:

```bash
LAB_AGENT=1 bash scripts/lab_demo.sh
```

## D. What to say when asked "is this just a wrapper around ChatGPT?"

- The model is one component. The project is the **server, tools, policy, helpers, tests
  and audit**.
- The model cannot run a command. It can only call 23 typed tools.
- Every state-changing tool is dry-run by default, allow-listed, validated twice and
  approved by a human.
- The helper is the only privileged code, and it is root-owned with a two-command sudoers
  rule.
- The lab demonstrates the full apply/rollback path without the model.

## E. Likely questions and short answers

| Question | Answer |
|---|---|
| Why MCP instead of a REST API? | MCP standardises discovery, schemas, resources, prompts and transports; any MCP host can use the server. |
| Why not let the model write shell? | An unrestricted shell makes prompt injection equivalent to account compromise. Fixed argv + allow-lists is the control. |
| What if the model hallucinates a unit? | The server regex + policy rejects it, and the helper checks the allow-list again. |
| What if `nginx -t` passes but the value is wrong? | Syntax is not intent. The human approves the diff; future work adds policy tests and health checks. |
| Can the model approve itself? | No. Approval is in the CLI; the server has a separate write gate. `--auto-approve` is an explicit demo flag. |
| Is the audit tamper-proof? | No, it is local JSONL. Future work: remote syslog and hash chaining. |
| Why Groq? | Fast OpenAI-compatible function calling, free tier, good latency on the test host. The provider is replaceable. |
| Does it work offline? | The tools do; the agent needs a model. A local model is future work. |
| What about Windows/macOS? | The server targets Linux systemd/nginx; the protocol and agent are portable, the tools are not. |
| What was the hardest part? | Making the change safe and reversible, not calling the LLM. |

## F. Recovery commands

```bash
# Service state
sudo systemctl status nginx
sudo systemctl reload nginx

# Helper state
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh status
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh list-backups
sudo -n /usr/local/libexec/linux-agent/nginx_param.sh rollback <id> --reload

# Remove the sudoers rule and helpers
sudo scripts/uninstall_privileged.sh

# Tests
make check
make test
```

Do not run `rm -rf` on `/etc/nginx` or `/var/backups/linux-agent`. The helper is designed to
restore, not to start over.
